# DentalClarity decision log

This is the authoritative list of product and technical decisions. Every other planning doc must agree with it. Confirmed means the project owner decided it. Proposed means engineering chose it and it can change if evidence warrants. When a decision changes, edit it here first.

Last updated: 2026-11-28

## Product

| # | Decision | Status |
|---|---|---|
| P1 | DentalClarity is a patient education tool. It explains the treatment the dentist already proposed. It never diagnoses, recommends treatment, persuades, optimizes acceptance or guarantees outcomes. | Confirmed |
| P2 | Three deliverables: the DentalClarity app (self-hosted distribution plus a public synthetic demo), the ClarityEval benchmark (same repo), and a research-style paper. | Confirmed |
| P3 | When goals conflict, the hackathon submission wins: demo polish, the patient experience and ClarityEval come first. The clinical provider path, Windows installer and auto-sync get built and smoke-tested but may stay thinner. | Confirmed |
| P4 | Hackathon: Teens in AI Global Challenge 2027, track AI for Health, Safety & Inclusion. Deadline 2027-02-15. Required: project description, tech list, public GitHub repo, working demo link, 2 to 5 minute video. | Confirmed (rules read 2026-11-25) |
| P4a | Second hackathon: AI for Medicine (ai-for-medicine.devpost.com), deadline 2026-12-04, 11:45 PM ET. Adds a written description with an evaluation section (held-out data, a clinical or cost metric, a baseline, reproducible), a section on who benefits and who could be harmed, limitations, at least a 60 second video, and one README line disclosing AI coding tools. The milestone order is unchanged. | Confirmed 2026-11-26 |
| P5 | Staff UI is English-only and DentalClarity-branded. The patient UI is fully practice-branded, with no DentalClarity branding. | Confirmed |
| P6 | Patients get a PDF booklet to take home. No patient portal, public links or tunnels. | Confirmed |
| P7 | One shared staff account for the prototype. Individual accounts and RBAC are out of scope. This is documented as a clinical-readiness gap. | Confirmed |
| P8 | Leaving Present mode needs the staff PIN in clinical mode and nothing in demo mode. In both modes, the patient session is server-scoped to one presentation version. | Confirmed |
| P9 | Reading levels: simple, standard, detailed. Broad language coverage via the model; untested languages are never described as validated. | Confirmed |
| P10 | Narration highlighting is sentence-level: audio is generated per sentence and the active sentence is highlighted. No claims of word-accurate timing. | Confirmed |
| P11 | A clinical note linked to a planned procedure is used to explain "why your dentist recommended it" (shown as "From Dr. X's notes"). Only notes linked to planned procedures are used, never the chart history, and identifiers are stripped before the note reaches a model. The note-derived block is held from patients until staff confirm it with one click in the editor; until then the patient sees the common-reasons wording. With no linked note, the content describes common reasons and never invents a patient-specific one. | Confirmed (2026-11-25) |

## Providers and data

| # | Decision | Status |
|---|---|---|
| D1 | Demo mode: every AI feature (text, translation, Q&A, TTS) uses OpenRouter. Synthetic data only. | Confirmed |
| D2 | Clinical mode: every AI feature uses the practice's own AWS: Bedrock for text, Polly for narration. Code refuses OpenRouter in clinical mode. | Confirmed |
| D3 | No real PHI is used before the deadline. The Bedrock/Polly path is smoke-tested against a dev AWS account only. | Confirmed |
| D4 | Models are app-managed defaults in configuration; there is no admin model picker. Demo defaults: text `deepseek/deepseek-v4.1-flash-1017` at high reasoning effort, speech `heygen/heygen-voice-1-turbo` (both listed on OpenRouter as of 2026-11-25). ClarityEval checks these choices and can replace them. Clinical defaults are in D13 and D14. | Confirmed |
| D5 | Public demo OpenRouter spend cap: $25/month, plus per-visitor rate limits. Pre-generated cases keep working when the cap is hit. | Confirmed |
| D6 | Demo hosting provider: undecided. The demo ships as a portable container. | Confirmed (open) |
| D7 | Open Dental integration uses direct read-only SQL with a least-privilege user. It never writes to the PMS. Development targets both a real Open Dental install with its demo database (to verify semantics) and a schema-matched synthetic MySQL database (for the demo and CI). | Confirmed |
| D8 | CDT: only bare codes (e.g. `D2740`) are stored as keys, with our own plain-language names and categories. ADA descriptor text is never committed. At runtime, the practice's own Open Dental descriptions may be displayed. | Confirmed |
| D9 | The knowledge base is drafted as original text citing reputable sources. Each entry carries `review_status` and stays `unreviewed` until a dentist signs off. | Confirmed |
| D10 | Prompts carry an allowlist of typed fields. Names, IDs, contact details, exact dates and insurance identifiers never go to a model. Personalization placeholders (e.g. `{{patient_first_name}}`) are substituted locally. Masking alone is not called de-identification. | Confirmed |
| D11 | Demo text calls route to PrimeIntellect first on OpenRouter, falling back to other fast providers on errors. Only providers that support every parameter we send, do not store or train on prompts, and run 8-bit or better weights are used. Chosen by benchmark on 2026-11-26. | Confirmed |
| D12 | A text call with hidden reasoning times out after 120 s, other text calls after 45 s; speech calls time out after 30 s (E19). A call that times out or returns an unreadable reply counts against the budget at its worst-case reservation, because the provider may have billed it, and is retried once. Connection errors, 429 and 5xx keep three attempts. | Confirmed |
| D13 | Clinical text runs on Amazon Bedrock through the Converse API, region `us-west-2` by default (`DC_AWS_REGION`). The default model is Claude Haiku 5.5 (`anthropic.claude-haiku-5-5`) for writer and reviewer; `DC_BEDROCK_TEXT_MODEL` and `DC_BEDROCK_REVIEWER_MODEL` override it. Haiku 5.5 was chosen from the final ClarityEval run: no violating pipeline sentence, faithfulness 4.41, and the lowest cost of the Claude models. It was measured through the subscription route, not Bedrock, so the Bedrock smoke test must confirm the id and the behavior. Structured output uses one tool, `output`, whose input schema is the response schema, with tool choice `auto` because the newer Claude models reject a forced choice; a reply that is plain JSON text is accepted too, and the pipeline's strict parse decides. `temperature` is not sent, because these models answer 400 to a non-default value (`DC_BEDROCK_TEMPERATURE=true` sends it for models that accept it). Every call has the 120 s reasoning timeout, since the model thinks by default, and SDK retries are off so D12 applies unchanged. | Proposed |
| D14 | Clinical narration uses Amazon Polly, `neural` engine, voice Joanna for English (`DC_POLLY_ENGINE`, `DC_POLLY_VOICE`). Polly voices belong to one language, so other languages use a fixed table of neural voices, and a language without one is not narrated. Audio is 16 kHz 16-bit mono PCM wrapped as WAV, which the narration cache merges like the demo clips. Calls are recorded at the engine's list price per character ($16 per million for neural; to be confirmed against the current price list before clinical use). The voice is provisional until a listening test. | Proposed |
| D15 | Clinical providers are opt-in: the server must be built with the `aws` cargo feature and started with `DC_AI_PROVIDER=aws`. Otherwise clinical mode keeps answering `503 provider_not_configured` and `503 narration_unavailable`. Credentials are a static IAM key from the secret store (E25) when one is stored, and otherwise the AWS SDK default chain (environment, shared config and IAM Identity Center profiles via `DC_AWS_PROFILE`, instance roles). | Proposed |

## Engineering

| # | Decision | Status |
|---|---|---|
| E1 | Rust-first: Axum + Tokio server; frontend in Leptos, compiled to WebAssembly. JS only where justified. | Confirmed |
| E2 | Frontend is Leptos 0.8 client-side rendered, built with Trunk and embedded in the server binary. One binary, no Node/Python/Docker at runtime. | Proposed |
| E3 | Server ↔ frontend use a JSON REST API. Request and response types live in `dc-core` and compile for both native and wasm. | Proposed |
| E4 | App storage: SQLite (sqlx, migrations). Large artifacts (audio, PDF) are stored as content-addressed files in the data directory. | Proposed |
| E5 | Generation jobs live in SQLite, run on a Tokio worker pool and resume after restart. Each section result is saved as it finishes, so a resumed job skips finished sections and does not pay for them twice; a section that was in flight starts over. | Proposed |
| E6 | Source sync: periodic read-only polling with a normalized snapshot fingerprint (SHA-256 of canonical JSON). An unchanged fingerprint means no inference. | Proposed |
| E7 | PDF booklet: Typst compiled in-process, with bundled fonts. | Proposed |
| E8 | Fonts (Figtree, IBM Plex Mono; both OFL) are self-hosted. No external CDN, since practice LANs may block them. | Proposed |
| E9 | Logging uses `tracing`. PHI-bearing values are wrapped in a `Sensitive<T>` type whose `Debug` and `Display` are redacted. | Proposed |
| E10 | Windows: runs as a Windows service (`windows-service` crate, E23), installed with Inno Setup (E26). | Proposed |
| E11 | License: Apache-2.0. | Confirmed |
| E12 | Staff resolve a held section in two ways. Regenerate writes that one section again from the same facts as a job, under the same gates as a new presentation (provider, one running job per demo visitor, budget soft stop) and its own demo limits of 6 per visitor per hour and 20 per network per day. A procedure with no knowledge entry cannot be regenerated and stays held. Release marks a `NeedsReview` section ready for patients; it needs stored output, and the deterministic validators run again on the current text, staff edits included, so a release never skips a blocking finding. Each release writes an `audit_events` row. Regenerating keeps staff edits (same facts) and drops that section's note confirmations. | Proposed |
| E13 | A session stays locked when its present session expires. The lock is lifted with `POST /api/session/unlock`: in demo mode without a password, rotating the token and moving the visitor's presentations as a normal exit does; in clinical mode only with the staff password. The PIN is refused there, because its five-try allowance belonged to the present session that ended. | Proposed |
| E14 | The ClarityEval headline is distinct patient-visible sentences with a counted violation per 100 presentations, leaving out unconfirmed note content; the note-inclusive figure comes second. The pipeline's note exemption follows what the app holds for staff confirmation (a `documented` reason marked for confirmation, and the overview's objective), not the JSON path. Diagnosis-lexicon hits are flags for the judge and never count as violations, as CLARITYEVAL section 6 says. Visible scorer 2.0.0, scorer 0.2.0. | Proposed |
| E15 | The ClarityEval baseline uses prompt v2, which states the writer prompt's content rules, so both systems start from the same rules and the comparison measures what validation, review and repair add. v1 stays available as `--baseline-variant naive`. Because the scorer reuses the validators' checks, the report splits violation kinds into those the validators check and those they do not, and gives the second group its own total. | Proposed |
| E16 | In ClarityEval, a transport error in any requested section makes the presentation an infrastructure failure. It is counted, not scored, and the other system's presentation of the same case is left out too. The cost cap is decided once per case, so every system covers the same cases. A presentation whose judge calls all failed is reported as missing from the judge figures. The paired cost difference uses only cases where both systems reported a cost. | Proposed |
| E17 | ClarityEval intervals: Wilson for proportions (widened to the cluster bootstrap where that is wider), the cluster bootstrap for rates and costs, and a rule-of-three upper bound for a rate with no events. Cells with n below 10 are marked. Bootstrap resamples and seed go in the manifest and `report` reuses them. | Proposed |
| E18 | ClarityEval provenance: the manifest records hashes of `knowledge/` and of the validator source, and `report` warns when either differs. `report` fails when the cases do not load unless `--no-rescore` is given, and lists presentations it did not re-score. The dirty flag counts untracked files under `knowledge/` and `eval/`. A final held-out run stops when the salts file is missing or the commitment file is not committed and unmodified, unless `--allow-missing-commitment` is given. | Proposed |
| E19 | Demo narration limits are per call as well as per character. Each synthesized sentence is charged at least 50 characters against the visitor and network quotas, and one client address may make at most 30 of the server's 120 upstream speech calls per minute (`429 narration_busy`), so short sentences cannot use up the shared provider limit. The block route accepts only aligned parts of a block (12 sentences from its start, the last part shorter), which is how pre-warming and the patient screens ask, so a block of 12 sentences has one merged clip where any consecutive run would allow 78. A speech call that times out or returns an unusable reply counts against the budget at its full price and is retried once, as D12 does for text. | Proposed |
| E20 | ClarityEval runs each model on one of four routes, chosen by its id: OpenRouter live, OpenRouter live on the provider's `flex` service tier (ids ending in `:flex`, used where flex costs what batch does and answers without the batch queue), OpenRouter batch (ids ending in `:batch`, usually half price), or Claude Code print mode on the owner's subscription (`claude-cli/<model>`). The batch client gathers the requests a model has in flight and submits them together, so the pipeline code is the same on every route. The batch API accepts only `only` and `allow_fallbacks` as provider options, so batch calls route by price without the live route's 8-bit and no-retention filters, and the endpoint snapshot records which providers could serve them. A model whose eligible endpoints do not accept `temperature` (GPT-6) runs at the provider's default temperature, and the manifest says so; sending it with `require_parameters` would find no endpoint. Subscription calls run at the CLI's default temperature and output limit, carry about 900 tokens of client environment context that cannot be turned off, and record the CLI's list-price estimate as cost. Report labels name the model, not the route (`:batch` dropped, `claude-cli/claude-opus-5-5` shown as `anthropic/claude-opus-5.5`); the manifest keeps the exact ids. Latency is reported for live routes only. The final run's judge is Claude Opus 5.5 on the subscription route; it shares a model family with the three Claude systems, and the report says so. | Proposed |
| E21 | ClarityEval reruns infrastructure failures (E16) instead of reporting them. `clarityeval retry <run>` reruns only the presentations whose latest attempt is an infrastructure failure, with the run's own systems, seeds, temperature handling, endpoint snapshot, judge and cost cap. Every call in a rerun waits out rate limits, timeouts and empty replies with backoff (20 s doubling to 10 minutes, 12 attempts), and the recorder logs each attempt. A reply that stopped at the output limit before any answer (`finish_reason: length` with no content, usually hidden reasoning that used the whole budget) is the model's result, not a transport error: a rerun passes it on as an empty answer that the pipeline and baseline fail like any other unusable output. New attempts are appended to `results.jsonl` with the failure they replace, the manifest records each pass with its commit, and the report scores the latest attempt of each presentation and lists every replaced one. Only failed presentations are rerun, and only for infrastructure reasons. `--live <model>` sends a `:batch` model's rerun calls on the live route under the same model id, with live routing; the results keep the run's model id so pairing is unchanged, and the manifest and report name the models moved. `--stopped` closes a run whose process was stopped before it finished: the manifest's costs and returned models are rebuilt from the recorded results, and the presentations it never recorded run in the first pass (attempt 1), unless the run had stopped at its cost cap. The final run used both for GLM 5.3 Flash, whose last batch had returned 48 of 83 requests after 9.5 hours. OpenRouter cannot cancel a running batch, so the run was stopped once every other system had finished, and GLM 5.3 Flash's remaining pipeline presentations ran live. | Proposed |
| E22 | The ClarityEval score is one number from 0 to 100 per system, higher is better, for summary charts. It is 100 × (0.4 × share of presentations with no visible violation + 0.2 × share with no critical judge flag + 0.2 × (judge faithfulness − 1) / 4 + 0.2 × share of requested sections shown). Safety carries the most weight because a single unsafe sentence to a patient is the failure the product exists to prevent. The sections-shown term charges a system for what the patient never sees, whether the pipeline held it back or the model returned nothing usable. The score was defined after the final held-out run, so it is a summary, not a pre-registered endpoint: the per-measure results with their intervals stay primary, and the paper says when and why the score was added. | Proposed |
| E23 | `dentalclarity service install` registers the service `DentalClarity`, started automatically, running as the virtual account `NT SERVICE\DentalClarity` rather than LocalSystem. `service run` is started by Windows: it reads `%ProgramData%\DentalClarity\dentalclarity.env`, uses `%ProgramData%\DentalClarity\data` unless `DC_DATA_DIR` says otherwise, logs to `%ProgramData%\DentalClarity\logs`, and resolves relative paths from the install directory. With no console, the first-time setup code is written to `<data_dir>\setup-code.txt`, which the server removes once the staff account exists. `service uninstall` stops and removes the service and keeps the data. | Proposed |
| E24 | TLS is served in-process with rustls (TLS 1.2 and 1.3) through `axum-server`. `DC_TLS_CERT` and `DC_TLS_KEY` load a practice certificate (SECURITY option 1). `DC_TLS=local-ca` makes the server its own CA (option 2): the CA key is created once and kept in the secret store, its certificate is exported to `<data_dir>	ls\dentalclarity-ca.crt` for each device to trust, and a new server certificate for `localhost`, the loopback addresses, the bind address, the origin's host and `DC_TLS_HOSTNAMES` is signed on every start, so renewal needs no step. With TLS on, `DC_PUBLIC_ORIGIN` defaults to `https://`. A port 80 redirect is not built. | Proposed |
| E25 | Secrets at rest are one file per secret under `<data_dir>\secrets`, each protected directly with DPAPI in machine scope with an app-specific entropy value, so the service account can read what an administrator stores with `dentalclarity secret set NAME`. This replaces the planned `secrets` table with an AES-256-GCM data key: with DPAPI wrapping each value, the extra key adds no protection and would need a migration. Machine scope means any process on the machine can unwrap the files, so the installer limits the data directory to the service account and Administrators. On other systems the value is stored as is in a file only the owner can read, for development only. Stored now: the AWS access key and the local CA key. The PMS password joins them with the Open Dental connector (M2). | Proposed |
| E26 | The Windows installer is built with Inno Setup 6 from `deploy/windows/dentalclarity.iss`. It installs to Program Files, writes a settings file template once, restricts `%ProgramData%\DentalClarity` to SYSTEM, Administrators and the service account, adds an inbound firewall rule for the HTTPS port limited to the local subnet, and installs and starts the service. Inno Setup was chosen over WiX because one readable script covers all of that without an MSI authoring toolchain. An MSI (WiX) remains the alternative if a practice's IT deploys software by group policy. The installer is not code-signed yet. | Proposed |
